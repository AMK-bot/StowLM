# Functional app developer notes

The Functional app runs fresh synthetic cases through the pipeline in the Planner's live mode at `/planner?live=1`. The Demo app uses `/planner?demo=1`. Routes and file shapes are below; the development contract and build plan they came from are not part of the public copy. Live runs are recorded in [`verification/VERIFICATION.md`](verification/VERIFICATION.md).

The engine is reached through the pipeline's engine slot, not from app code: the planning worker hands the voyage packet to the runner's `run_packet` (`experiments/mvp/pipeline/runner/`), whose `engine_call` calls the binding's `execute_brief` (`experiments/mvp/pipeline/binding/adapter.py`). The runner then rechecks the returned plan with the full checker and every confirmed instruction and classifies it on the rule-tier ladder before the app draws or packages anything. Engine 0.13.0 is the only engine wired in; no third-party engine has been ported (see "The engine slot" in the repository README).

Run from the repository root with Python 3.12 through uv:

```sh
uv run python -m app --functional --port 8794
```

Open `/planner?live=1`; `/functional` and `/functional.html` redirect there. With `--functional`, `/` also redirects there; other launches keep the original root page. Add `--v6` to serve both apps from the same server; launch prints both Planner links. `--functional` alone does not wait for the default v3 instance to load. Port 8792 is reserved for the existing demo server; leave it alone. The server serves Planner assets with up to three lowercase alphanumeric suffixes, such as `planner-live-intake.js`; obsolete Functional-page assets are no longer routed.

The reader uses the adopted adapter recorded in `experiments/mvp/reader/v3/results-final/final-adoption-d266.json`, or `--reader-adapter DIR`, and base weights at `models/glimmer-30b-4bit`. Missing adapters or weights leave the reader unavailable while the server starts; a present adopted adapter with the wrong checksum refuses launch. The reader model loads lazily at the first reading and is shared by the server. `GET /api/functional/status` reports availability without loading a model or making an API call. Continuing with generated cargo or no instruction requires the planner's explicit choice.

Bring your own Meta Model API key. Enter it in the app, set `MODEL_API_KEY` in the process environment, or copy `.env.example` to a private repo-root `.env`; `--env-file PATH` selects another file. A small `KEY=VALUE` parser reads that file at launch without executing or expanding its contents, and existing environment values win. Paid calls also require consent through the app or `STOWLM_ACCEPT_PAID_CALLS=1` (`SPARK_CREDIT_READY=1` remains accepted). The launch cap uses the model layer's default (currently $10.00), preserving explicit caps from the environment, env file or app. Spark and Voice share a launch budget with separate client ledgers under ignored `spend/`, never the project's accounts.

`POST key` accepts `key`, `accept_paid_calls`, `cap_usd`, and optional `save_to_env_file`. Keys stay in server memory and enter authorized worker environments only; they are never echoed or written to call artifacts or logs. Explicit saving writes repo-root `.env` with mode 0600; it remains a plaintext local secret, ignored by Git. `DELETE key` disables the launch's credentials without editing the environment or an existing `.env`. These routes require a localhost or 127.0.0.1 Host and reject cross-origin mutations. `status.key` contains only `present`, `source`, `paid_calls_accepted`, `cap_usd`, and `spent_usd`.

The API prefix is `/api/functional/`:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `status`, `options` | Availability, engine status, form options and fresh seed |
| POST / DELETE | `key` | Configure credentials, consent and launch cap, or forget the launch's credentials |
| GET | `calls` | Most recent 50 calls, newest first, in `{"calls": [...]}`; each row has `id`, `created_utc`, `state`, `ship`, `boxes` |
| POST | `calls` | Start fresh case generation; returns 202 |
| GET | `calls/<id>` | Poll the full call view, stages and outcome |
| POST | `calls/<id>/papers`, `answers` | Upload/paste papers, choose the generated load list or selected generator records, and resolve intake questions |
| POST | `calls/<id>/audio`, `read` | Transcribe audio or read an editable sentence; returns 202 |
| POST | `calls/<id>/confirm` | Confirm the exact reading, sentence hash and rule hash |
| POST | `calls/<id>/plan` | Start a fresh `live` or `standard` engine attempt on the same assembled call, with a confirmed instruction or explicit `none`; returns 202 |
| POST | `calls/<id>/stop` | Stop the call's worker process group |
| GET | `calls/<id>/plan-view` | Checked plan data, or 409 with a plain reason |
| GET | `calls/<id>/planner/<name>` | Live Planner payload: `ship`, `boxes`, `plan-before`, `plan-after`, `moves`, `meters`, `checks`, `package`, `state`; unknown names return 404, unavailable plans 409 |
| GET | `calls/<id>/file/<name>` | Whitelisted generated papers, package files, outcome or case record |

POST bodies and errors are JSON. Uploads use `text` or `data_b64`, with a 10 MB limit. Generation, intake, assembly and planning run in subprocess workers; voice and reading run in daemon threads. Poll the call view after a 202. One engine job may run per server; another returns 409. Without `--functional`, the Functional API returns 404 with launch instructions.

Read-only routes do not acquire the server-wide mutation lock. Mutations and completion updates serialize per call, with brief shared locks for job ownership and the engine reservation. Call polls check credential presence and consent without reading the paid ledger. Requests taking over one second produce a stderr route template and elapsed milliseconds, excluding bodies, queries and document names.

Cargo uploads accept nonempty UTF-8 text/CSV or PNG, JPEG and WebP pictures; PDFs are unsupported. WAV headers, mono PCM16 format, 16/24 kHz rate, non-silent frames, duration and completeness are checked before any transcription starts. Invalid inputs return 400 without launching work.

Audio requests accept `origin: "browser"` or `origin: "upload"` (the default). This host-supplied origin is saved in `voice.json` and exposed as `voice.origin`; voice stage notes say “Recorded in this browser” or “Uploaded audio”, with an error reason appended if the stage fails. The independent planner-set `generated` boolean (also accepted as `generated_voice`) defaults to `false` and is retained as both `voice.generated` and `voice.generated_voice` for the live upload UI; it labels synthesized evidence “Generated voice” without changing how the audio reached the app. Conflicting aliases are rejected. The app cannot infer whether an uploaded recording was synthesized.

Each cargo document may include host-supplied `role`, `booking_ref`, `complete_booking_list` and `synthetic` metadata. Roles are `booking`, `shipping_instructions`, `vgm`, `dg_declaration`, `gate_slip`, `reefer_list`, `oog_list`, `amendment`, `correspondence` or `unspecified` (the default). Booking references are text or null; list-completeness and synthetic flags are booleans. The app preserves these in `papers/meta.json` under `documents` and passes them to `read_papers`; it does not infer authority from filenames or model output. The call view includes the roles and booking references. A host-supplied `container_ids` list may declare a booking's roster; the worker validates it against the call's load list. Uploaded groups without authoritative membership are read together once against the call roster, rather than separately producing duplicate full-roster rows.

Send `{"use_generated_papers": true}` to the papers route to read the fresh synthetic paper set through Muse Spark. The worker loads `papers/generated/manifest.json`, validates its call-relative file paths and preserves its roles and booking references. The call view labels each file “Synthetic document” with origin `generated`. Send `{"use_generated_load_list": true}` to continue directly with the generated load list; that separate choice skips model intake. Credit its stage as “Generated load list · software, no model call”; the Spark chip applies only when Spark actually read papers. Choose only one papers source per request.

For selected boxes with an open equipment-review or missing-OOG-dimensions question, the planner may instead send `{"use_generator_records_for": ["<container-id>"]}` to the same papers route. This is an explicit per-box choice to use the generator's record, not another paper reading or an answer supplied by a model. The list must be nonempty, contain unique IDs from this call's base load list, and be the only papers choice in the request. No API key or paid call is needed when the required intake receipts are already retained. This is a pre-plan intake choice: the existing papers-route guard prevents changing cargo after any engine run. Planning again on an existing call changes its instruction choice or profile, not its cargo.

This choice supports only the frozen intake's `unsupported_equipment` question on `iso_type` and `missing_oog_declaration` question on `oog`. Each selected box must occur exactly once in the retained intake and have one of those open review questions. Another question on that box, an unknown box, a duplicate booking row, or missing verified generator OOG dimensions prevents the choice; it does not authorize a general correction of accepted rows or DG declarations. Questions belonging to other boxes remain open. The worker assembles only once the effective intake is complete.

`functional_models.merge_generator_records(intake_view, base_instance_path, box_ids)` validates and copies the selected complete generator rows without a model call, ledger operation or file write. It preserves the other intake rows and the original cumulative reading charge. Its private `raw` uses schema `stowlm.functional-generator-merge/1`, retaining `source_intake`, `generator_rows`, `base_instance_sha256`, `base_file_sha256`, the explicit choice reason and zero incremental `cost_usd`. Public `generator_choices` records each selected `box`, `origin: "generator"`, reason and `closed_questions`. Original paid child-receipt files remain intact; if the planner previously chose the full generated list, the worker reconstructs the retained verified booking readings before applying the selected records.

The effective intake also exposes `generator_record_ids`, `row_origins` (`spark` or `generator` by container ID), and `origin_label`. Its label says “Muse Spark, with N boxes from the generator (not read by a model)”. The call view's `load_list.origin` uses that mixed label; its rows expose `origin: "muse_spark"` or `origin: "generator, not read by a model"`. The software choice appears as a zero-cost answers stage, retaining historical model charges. These row-origin fields are app provenance and are removed before strict Container validation in the voyage packet. Selecting generator records reassembles the call and invalidates its current reading and confirmation; planning then requires a newly confirmed reading or explicit no instruction.

The public booking progress reflects questions closed by the effective mixed intake; the original paid booking index and child files remain unchanged. A `constraint_unavailable` result supported by the runner's necessary full-load proof keeps the runner's scoped refusal without an app sentence denying that proof. Unfinished searches, timeouts and refusals without proof retain the uncertainty sentence. Proof classification uses the frozen runner's own metadata policy, rather than guessing from the message on screen.

Intake groups papers by their host-supplied `booking_ref`; papers without one form a single group. Newly generated bookings contain at most six boxes; older calls keep their existing booking boundaries and evidence. The worker allows up to six active booking reads and merges their receipts with `functional_models.merge_intake_views`. Each booking has its own measured stage, box count and cost; the merged intake view sums the booking costs. An answer cut off by the model's output limit is a failed attempt with its plain reason; none of that answer is used.

Before each booking starts, the scheduler acquires its first authoritative request grant with `functional_models.grant_call(call_id=..., booking_ref=...)`. A denied grant returns `None`; the scheduler waits for active work to finish or, when nothing is active, explains the cap refusal and retained readings. Up to six booking reads may be active. An app-owned `complete_documents` adapter supplies a separate granted client ledger for each actual request. It preserves the frozen intake's initial request and at most one schema-only repair; the repair obtains a fresh grant after the first request settles. Transport, credit and billing errors do not trigger another request. One slow HTTP request therefore does not hold another booking's client lock, and a repair does not incorrectly reuse the first request's exhausted local allowance.

Every request response or failure has private evidence under `intake/requests/<attempt_id>/<evidence_id>.json` before unused allowance returns to the launch pool. Booking completion then saves its full receipt, compact index and progress before releasing any remaining allowance and filling another slot. Failed or cancelled work also closes its grants through the accounting API; the worker never edits billing records itself. A denied schema-repair grant means that repair request was not sent; its initial request may already have incurred a charge.

`spend_status` separates measured `spent_usd`, request `held_usd` (also `holds_usd`) and unused active `grants_usd`. Their sum is `committed_usd`; the remaining cap determines `room_for_calls` using `hold_usd_per_call`. Allocations and conservative holds are not charges or predicted booking costs. The current frozen intake reserves $1.384448 per model request, derived from its token bound and the client's prices. A default request grant covers that reservation. A schema-repair retry requires another admission decision and can be refused when the launch lacks room; one grant does not guarantee that the entire booking will finish.

The launch coordinator allocates grants atomically under a short registry lock. Spark and Voice hold only their own client-ledger locks during HTTP calls. Status uses accounting snapshots, and cap changes use the coordinator; neither waits for a model client's HTTP lock. An incomplete trailing write in an active client ledger remains covered by its grant, while invalid complete records fail closed. `release(grant)` returns only unused allowance: measured charges and pending or unknown billing remain accounted for. Stopping a worker never turns unknown billing into free capacity. A cap change affects new admissions; it does not revoke allowances already granted to active calls. Increasing the cap requires explicit planner authorization.

The model API accepts `grant_call(cap_usd=None, *, launch_id=None, call_id=None, booking_ref=None, hold_usd=None, cap=None, refusal=None)` and returns an opaque grant or `None`. On denial, an optional `refusal` dictionary receives safe accounting figures from the same admission decision. `release(grant)` is idempotent. A supplied grant remains the caller's responsibility; `read_papers` and `transcribe(..., grant=grant)` release only grants they acquire internally. Voice allocates its own duration-based grant and passes its identity to the isolated credential-bearing worker. Launch budgets and per-request ledgers stay under ignored `spend/`; credentials are never part of either record.

Retrying the same papers resumes matching booking receipts instead of paying to read them again. Reuse requires matching measured document bytes, host authority metadata and the scoped base instance; changing those inputs invalidates reuse. Completed siblings remain available when another booking fails or reservation capacity runs out. An incomplete merged intake does not advance to assembly. Planner answers update the relevant child receipts in software without another model reading; their charge is zero.

The global generated `load-list.csv` is excluded from booking reads. Each generated booking uses a scoped base under `intake-bases/b000N.json` whose load list contains only that booking's verified container IDs. The intake view retains the legacy summed `read_wall_s` and `read_cost_usd`, plus separate `answer_wall_s` for software answer merging. Do not label summed booking time as elapsed time. Answers stages credit “Planner's answers” on this laptop, with no model and zero incremental cost.

`intake-accounting.json` supplies the same safe accounting fields exposed in the public intake view:

| Field | Meaning for the UI |
| --- | --- |
| `elapsed_s` | Elapsed time for this intake attempt, including overlapping work and queueing |
| `booking_wall_s` | Cumulative sum of booking processing time across accepted and failed attempts; not elapsed time |
| `spend_wait_s` | Measured wait after a first-grant refusal until admission, broker overhead and repair-grant acquisition; excludes queueing solely for a concurrency slot |
| `settled_cost_usd` | Cumulative settled usage for this call across intake attempts, including failed requests; conservative holds remain separate |
| `incremental_cost_usd` | Settled usage in this attempt, including failed requests and excluding reused readings |
| `completed_bookings` | Valid persisted child readings, including those still needing planner answers |
| `kept_bookings` | Matching child readings reused from earlier attempts |
| `unsent_bookings` | Bookings whose initial request was not submitted in this attempt; excludes reused readings |
| `open_questions` | Unanswered questions in the retained valid child readings |
| `cap_stop` | Null, or the atomic admission facts for an unsent initial or schema-repair request |

`cap_stop` carries `booking_ref`, `sent: false`, `charged_usd: 0`, `request_kind: "initial" | "schema_repair"`, `spent_usd`, `holds_usd`, `grants_usd`, `hold_usd`, `cap_usd`, and the four booking/question counters above. The accompanying `message` explains the unsent request, retained readings and outstanding questions, says nothing has been planned from a partial reading, and directs the planner to the API key panel. `papers.cap_refusal` and the matching `papers.bookings[]` row's `cap_refusal` expose those facts with a `reason` alias for the live panel. Compact booking rows also expose `kept` and `open_questions`. UI code must distinguish an unsent repair request from an entirely unsent booking.

The call view's `stages` contains each stage instance once, in first-start order, with the latest status replacing its running row. The underlying `stages.jsonl` retains every update. Booking stages carry an `instance_id` so concurrent groups and later answer rounds stay distinct. Reader provenance is explicit: `provenance` is `model_call`, `runner_revalidation`, `runner_no_instruction` or `no_instruction`, and `model_call` says whether a model was invoked. Runner reader rows additionally carry `source: "runner_receipt"` and a `revalidation` boolean; actual model reads carry `source: "model_call"`. A `runner_revalidation` stage additionally binds `reading_id`, `sentence_sha256` and `rule_sha256` to the confirmed reading. UI code must use this evidence rather than infer a second call or revalidation from journal order; a later reading after confirmation is still an actual model call. Failed aggregate intake stages expose `cost_scope: "cumulative_booking_total"`, `cumulative_cost_usd` and `incremental_cost_usd`; their cumulative total is not an extra charge to add to the itemized bookings.

Runtime files live in the ignored `calls/<call_id>/` folder beside this README. `request.json`, `case.json` and `base-instance.json` record the fresh case; `papers/` holds received bytes and `papers/generated/` holds labelled synthetic papers. `intake.json`, `assembled-instance.json`, `context.json`, `envelope.json`, `voice.json`, `readings.json` and `confirmation.json` record subsequent stages. `packet.json` is the voyage packet handed to the runner. Each engine attempt owns a fresh `runs/<n>/` folder containing the runner's `outcome.json`, `events.jsonl` and `package/`. The `run` symlink points to the latest attempt, preserving existing `run/...` readers. Older calls whose only output is an original `run/` directory remain readable. `stages.jsonl` supplies provenance, timings and costs; `worker-<step>.log` contains diagnostic traces while the API shows plain errors. Runtime cache files, if any, belong in the ignored `cache/` folder.

After an engine attempt finishes or stops, the planner may plan the same assembled call again. Send another `POST calls/<id>/plan` with the desired profile and `instruction: "confirmed"` or `instruction: "none"`. The server allocates the next integer attempt number and records it as private `worker-control.json.attempt`; callers do not select the number. This starts a fresh search, preserving prior attempt files. It reuses the call's existing cargo and intake evidence; it does not pay to read the papers or invoke the Reader again. A confirmed instruction is revalidated by the runner against its exact confirmation. Explicit `none` supplies an empty brief even when the call has past readings or confirmations. A newly requested model reading remains a separate model call requiring confirmation.

`attempts.json` retains compact engine-attempt metadata. Each record has `attempt`, `instruction` (`confirmed` or `none`), `sentence`, `reading`, `profile`, `status`, `wall_s` and `started_utc`; sentence and reading are null for an empty brief. Finalization adds a private `message`. Each attempt's `attempt.json` captures its submitted settings and final status, and its `packet.json` preserves the exact packet passed to the runner. The latest call view exposes `run.attempt`, `run.sentence` and an `attempts` list containing up to ten earlier attempt records, excluding private messages. Stage views belonging to an engine attempt carry `attempt: <n>` so engine, checker, ladder, package and reader-revalidation evidence stay associated with the search that produced them. Instruction reading, voice and confirmation stages are tagged with the upcoming attempt number. Intake attempts and their private request IDs are a separate history. Replanning an older call first retains its original `run/` bytes as `runs/1/`; legacy metadata may have a null start time or reading ID when the old evidence does not identify them.

The current plan and package always come from the latest numeric `runs/<n>` directory, including while that directory is still empty or its search is running. An earlier checked plan is retained as history and is not silently presented as the new attempt's result. Planner payload caches distinguish attempt folders; payload builds and attempt rotation share a per-call lock so the gate and source hashes refer to the same attempt. Call polls and status remain outside that lock. The current attempt must pass the same full-checker and confirmed-instruction gates before its plan is drawn. Allowed outcome and package downloads can use stable `file/runs/<n>/...` URLs; `file/run/...` addresses the latest attempt.

The public `outcome` adds `attempt`, `engine_instruction_infeasible` and nullable `engine_instruction_evidence`. The evidence object contains `source: "runner_evidence"`, `certified_cargo_infeasible`, nullable `certified_bound` (`status`, `stop_reason`, `scope`, `cost_cap`, `improvement_target`) and `masters` rows (`deck_tiers`, `status`). Scope is limited to 1,000 characters and masters to 32 rows. Cargo-no-room wording requires a confirmed instruction and certified infeasibility without a cost or improvement cutoff. Threshold infeasibility does not support that wording; masters-only observations are described as the tested master relaxations. The app preserves the runner's raw message and files. After a standard-profile no-plan result it appends: “This run already used the standard profile; with a confirmed instruction, try a looser one or plan with no instruction.” A late raw result from a stopped attempt remains unavailable for drawing even after another reading changes the call state.

Per-booking receipts no longer repeat their full raw evidence inside the index. `intake-bookings.json` uses schema `stowlm.functional-intake-index/1` and a `bookings` list. Each entry has `booking_ref`, `status` (`pending`, `done`, `needs_answers` or `failed`), `boxes`, `wall_s`, `cost_usd`, `file`, `sha256`, `documents_sha256`, `base_sha256`, `spend_wait_s` and `request_evidence`. `file` points to `intake/bookings/<safe-ref>-<contenthash16>.json`; `sha256` verifies those file bytes, while the other two hashes bind normalized source metadata and measured document hashes to the scoped base JSON. `request_evidence` lists private attempt files with their settled cost, held amount and elapsed time. Pending entries have no completed receipt to reuse.

`intake-view.json` is the compact intake view without `raw`; while reading, its `progress` contains `completed_bookings`, `total_bookings` and `pending_bookings`. The full merged `intake.json` remains private evidence for software processing. The call view uses the compact view rather than transmitting raw receipts on every poll. `papers.bookings` exposes the index's `booking_ref`, `status`, `boxes`, `wall_s`, `cost_usd`, `file` and `sha256` fields without opening individual receipt files. Legacy inline indexes migrate to content-addressed child files only when their evidence can be matched to the current inputs. `intake/legacy-index-<oldindexhash>.json` and `intake/history-index-<indexhash>.json` retain compact pointers to older evidence; unmatched or unverifiable receipts are preserved but do not authorize reuse. Receipt provenance continues to name the code that originally ran; migration alone does not establish a fresh model call or validation under a newer policy. A failed intake can retry the papers or explicitly choose the generated load list.

The worker leaves the runner's source directory unchanged so its immutable policy fixtures remain readable. Cache directories and the package writer's signing-key directory are redirected separately; changing the runner's source root also changes its fixture lookups and prevents planning.

Compatible implementation additions to the contract: each public reading exposes `sentence_sha256` and `rule_sha256` for exact confirmation. Private `worker-control.json` holds `adapter_dir`, `model_dir`, and step options (`documents`, `answers`, `use_generated_load_list`, `use_generated_papers`, `use_generator_records_for`, `profile`, `instruction`, `attempt`); `worker-state.json` holds `state`, `message`, and worker-written `step`. Generator-choice receipts, `generator_choices`, `generator_record_ids`, `row_origins`, `origin_label` and public load-list row origins are described above. Engine-attempt folders, `attempts.json`, `run.attempt`, the call view's earlier `attempts`, and stage `attempt` numbers are described above. `papers/meta.json` holds normalized document metadata, with `papers.json` retained as a compatibility copy. Rows contain `name`, `media_type`, `path`, `bytes`, `sha256`, `origin`, `role`, `booking_ref`, `complete_booking_list`, `synthetic`, and generated rows' `label`. The compact intake index, child receipt files and public view are described above. `admission.json` holds the runner's real capacity reading, or explicitly `waived` and measured `load1`. An empty `.stages.lock` protects atomic journal replacement between processes. These are runtime files only. Cargo changes invalidate prior readings and confirmation; repeating a plan keeps the same assembled cargo and creates another engine attempt.

Cases outside the headline envelope stop before planning: only 500–800 TEU feeders, including tiny and small sections. `call.runner_envelope` and `runner-envelope.json` contain the runner's own gate; `call.envelope` contains the combined app gate, including the headline ship restriction. A tiny or small section of a 1,700 TEU ship may pass the runner gate while failing the headline restriction; UI labels must keep those results separate. An empty brief uses no reader instruction. The worker re-validates an exactly confirmed reading without a second model call and records `functional_app_planner_click`. The engine admission helper may waive stale fleet telemetry when no fleet is running; its decision and measured load must be visible. The default `standard` engine deadline is 1,800 s; selectable `live` is 720 s. These are engine deadlines, not whole-run guarantees. Live readings retain `wall_s` and `cold_load_s` separately; reader stages also expose optional `cold_load_s`.

Stopping retains ownership of the recorded worker process group through bounded TERM/KILL cleanup. Shutdown joins its watchers outside the lifecycle lock. Stopped stages receive terminal failed records. If owned-group cleanup cannot finish, the engine remains reserved; restart the server after resolving that cleanup failure.

Only an L0 full-checker pass may be labelled “Passes the full checker”. Relaxed results name their level, every broken rule and boxes ashore; partial plans show the percentage aboard. L4 needs a person's sign-off, and L5 is labelled not safe to sail. A failed search does not prove that no plan exists. Extra crane lifts include rehandles now and projected at later ports plus hatch-cover lifts; timings are measured on this machine in this run. All ships, cargo, documents and port activity here are synthetic or simulated.

Use `run.status: "stopped"` and its retained incumbents to explain a planner stop: checked plans may have been found even though none was released. The “No checked plan found” suffix applies only to runner outcomes `no_checked_plan` and `constraint_unavailable`, never to every failure or missing package. Advice displayed by the Functional app must fit its controls: 1,800 s is its longest engine deadline, so suggest a fresh call with lower fill or fewer boxes when that budget is exhausted. Replace advice to use a recording with “Retry, or start a fresh call. The Functional app never uses recordings.” Preserve the runner's original evidence separately.

`run.instruction` is the explicit `confirmed`/`none` plan choice (null when unknown on an older call); `run.confirmed_reading` is the selected reading id only for `confirmed`. Export captions must use that choice and actual model-call stages, rather than treating a past confirmation as proof that its instruction was used. Planner-stop facts persist as `worker-state.json` fields `stopped`, `stop_reason` and `step`; a stopped call exposes no released outcome or gated plan payload, including after reload.

Run only the app tests during implementation:

```sh
uv run pytest app/tests/test_functional_api.py app/tests/test_functional_worker.py app/tests/test_functional_guard.py -q
uv run pytest app/tests/test_server.py app/tests/test_planner_shell.py -q
```

These tests use fake cases, models and runner calls: no network, paid calls, MLX model load, engine search or browser. The guard scans Functional Python and static sources for replay-only source references. Do not run pipeline test suites in place: they can rewrite pinned fixtures. A local HTTP smoke check may fetch `/functional` and `/api/functional/status` from a server started on 8794 without an API key, verify unavailable reasons, then stop only the server process you started.

Passing fake tests and the unavailable-stage smoke check does not establish live end-to-end success. Live runs on fresh seeds with the actual model stages, planner confirmation, engine, checker and package, including the ones that didn't pass, are recorded separately in `verification/VERIFICATION.md` (3 Nov 2026); they are anecdotes, not a rate. No live result is claimed by these developer checks.
