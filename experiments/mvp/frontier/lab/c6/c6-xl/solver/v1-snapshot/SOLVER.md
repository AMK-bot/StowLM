# CPU assignment scaling variant

Entry: `solver/method.py:propose` and `solver/method.py:finish`; use the copied ladder runner in this experiment. Suggested first measurement: 240 s proposal, 60 s finish, one try and one worker. Runtime is cold: no earlier plan, assignment, recipe or ballast is read. The unchanged replay and full checker decide legality and passes. This is a heuristic, not a proof of map feasibility or infeasibility.

## What grows

The graph has one vertex per box and one per physical slot. An edge assigns that box to that slot. A 40-foot edge consumes two physical cells. Support, order, weight, height, moment and securing rows constrain chosen edges. A lift is measured from the resulting real loading replay and D15 fixed-stow later-port projection; it is not an edge count.

If boxes and slots grow together, forming every eligible edge costs roughly the square of box count. C5 forms that entire Python list before throwing most of it away to retain 150 random slots per box. The resulting matrix also grows by dozens of coefficients per edge, especially securing rows. Its Python lists can use much more memory than the final sparse matrix. Every dive LP is solved afresh by SciPy; retaining a sparse matrix does not retain a HiGHS basis. The CP-SAT tail introduces one Boolean per surviving free edge and has combinatorial search. None of these facts implies a polynomial wall-time bound.

Before proposal, the original search engine also materializes a dense slot-by-cell incidence matrix and multiplies box-by-slot eligibility by it as int32 arrays. With ship/cargo dimensions growing together, that performs roughly cubic work even though every slot touches at most two cells. A physical generator interruption identified the same expression on its path; a later stack location inside ClassFlow alone does not establish ClassFlow as the expensive stage.

Another initializer copied an entire box-by-slot table for every page before selecting that page's columns. That temporary work is roughly cubic when ship and cargo grow together; it is avoidable indexing work, not optimization.

## Implemented changes

* At plug-in import, install a private **search-engine constructor** adapter before `Problem.init`. For more than 500 demanded load boxes, replace only the original dense cell-incidence multiplication with exact Boolean OR scatter over each slot's at-most-two cells. Work is O(boxes × slots); output remains the identical box-by-cell compatibility array. `ClassFlow` grouping, capacity screens and all other constructor lines remain unchanged. The full original constructor is called verbatim at 500 load boxes or fewer, even if parent inventory and yard blockers exceed 500. The original constructor block is asserted before transformation and any mismatch fails closed. No checker or pinned-runtime source file is edited. Engine construction/projection timings are exposed in method metadata.
* For more than 500 boxes, construct only a restricted edge set, one box at a time. Retain all eligible tiers on each chosen page, so a chosen upper tier has supporting tiers available in the graph. Choose at least one page in every available hold/deck × fore/mid/aft × port/starboard stratum, then random pages until the target of 64 edges is reached. Keeping whole pages and mandatory strata can exceed 64; actual min/median/max are emitted. Special box eligibility always comes from the original static mask. This avoids the dense all-boxes edge list and gives support/balance alternatives that unrelated slot sampling may miss.
* At 500 boxes or fewer, retain C5's exact candidate order, seeded random150 choice and dive/tail choices. The existing feeder regression maps contain 300–401 boxes. Caching may change wall-time-bounded search outcomes; exact equal LP matrices do not promise identical end-to-end timings or passes.
* Select a page's static mask through `np.ix_`, directly selecting the required submatrix. It returns the same bytes without copying the whole box-by-slot table first.
* Cache box forces. Cache nominal securing coefficient matrices by **exact** motion-acceleration tuples and tier heights. Mirrored positions with identical accelerations reuse computation; every physical page still has its own unchanged capacity rows. No approximate aggregation of masses, cells or constraints occurs.
* Record pair counts, matrix nonzeros and sparse bytes, assignment construction and LP build times, every LP solve, every tail build/solve, dive, exchange/repair, sequencing/replay and full check. The outer runner records process peak memory and total stages.

The restricted graph can fail when the complete graph has a feasible stow. No pricing oracle adds missing negative-reduced-cost edges, so this is **not column generation** and has no full-graph LP bound. A no-stow result means no plan found in this bounded heuristic. The dive, integer tail and outer GM adaptation otherwise remain C5's, which makes this a focused candidate/memory intervention rather than an algorithm replacement.

## Papers and alternatives

* Sadykov, Vanderbeck, Pessoa, Tahiri and Uchoa (2019), [Primal Heuristics for Branch and Price: The Assets of Diving Methods](https://pubsonline.informs.org/doi/10.1287/ijoc.2018.0822): restricted pools and diving motivate this heuristic. We do not implement their complete algorithm.
* Lenstra, Shmoys and Tardos (1990), [Approximation algorithms for scheduling unrelated parallel machines](https://doi.org/10.1007/BF01585745), inherited from C5: assignment first, integer completion next. Their guarantee has one machine-capacity row; our many side rows do not satisfy that setting, so no approximation guarantee is claimed.
* Applegate et al. (2021), [Practical Large-Scale Linear Programming using Primal-Dual Hybrid Gradient](https://arxiv.org/abs/2106.04756): first-order updates use sparse matrix-vector operations and could remove factorization costs, but they do not remove the integer tail. [Current HiGHS documentation](https://ergo-code.github.io/HiGHS/dev/solvers/) describes PDLP, while this environment's SciPy `linprog` interface exposes `highs`, `highs-ds`, `highs-ipm`, not a PDLP method. We did not install a new solver or claim a PDLP experiment.
* Bay decomposition could leave cargo mass and moments as global coupling, but box uniqueness, OOG conflicts and spanning 40-foot cells must also be handled. We did not replace those constraints with an unsupported separability assumption. Sinkhorn solves a regularized transportation core; support/order, securing and moment rows remain, and a fractional transport solution is not a legal stow. Neither algorithm is claimed implemented.

The search constructor adapter reads the pinned runtime's `stowage.feasibility._engine.IncrementalEngine.__init__` through `inspect`, asserts exactly one expected projection block, and compiles a process-local search-only copy with that block replaced. It is not a replacement capacity rule.

Sources copied privately: C5 `method.py`, `gap.py`, `stow.py`, `rows.py`, `chainlab.py`; C4 c2-layout `pages_sight.py` (as `xl_sight.py`), `pages_balanced.py`, `pages.py`, `pages_base.py`, `pages_fast_dense.py`, `repair.py`, `ballast_opt.py`, `physics.py`. Only path/cache roots are changed in copied ballast code. The original checker, source engine and parameters are unchanged. The allowed C1 `e9fix.install` is imported.

## Verification

`test_scaling.py` and `test_fast_engine.py`: **11 tests passed against the pinned runtime**. The eight new engine tests include 60 randomized exact comparisons with the original integer product (empty dimensions, duplicate cells and long slots), exact ClassFlow rows/classes/compatibility/flow, the demand-count threshold including large inventories, and idempotent constructor installation. The original three tests remain: One compares the entire original and copied LP (objective, sparse inequalities and equalities, bounds) with exact array equality after original seeded150 sampling; one checks XL seeded determinism, whole-page tiers and available hold/deck coverage; one proves the indexing replacement returns the exact original submatrix. No stored/sealed maps are used by these tests. Numeric execution used one thread and `nice -n 5`; macOS rejected setting process niceness with `Operation not permitted`, so the command continued without the requested priority change. Larger-map full-check results belong to the scoring artifacts, not these unit tests.
